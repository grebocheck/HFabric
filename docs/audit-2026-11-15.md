# Аудит спрощення та стабільності HFabric — 2026-11-15

Стан коду: `ac6548a` (`Fix image queue validation and simplify editors`).
Аудит виконано на Windows, Python 3.12.10, Node 24.17.0. Дата оцінки
прострочених винятків: 15 листопада 2026 року.

Знахідки нижче описують цей вихідний commit. Статус подальших виправлень
наведено в розділі «Реалізація першого пакета після аудиту» наприкінці документа.

## Висновок

Проєкт має добру основу: один worker для основної GPU-черги, арбітр із
перевірками переходів, Alembic, ізольовані STUB-тести, атомарне JSON-збереження,
згенеровані API-типи та браузерні перевірки. Її варто зберегти.

Поточний пріоритет — виправлення втрати даних, відновлення після помилок і
власності над GPU-ресурсами. Значна частина складності зосереджена у
контролерах React, аудіопідсистемі та неявних контрактах image mixins.
Попередні розділення файлів допомогли навігації, але залишили ці залежності.

Поточні release gates також мають проблеми: Knip знаходить зайвий експорт,
Python dependency audit повідомляє advisory findings, усі п'ять GPU advisory
exceptions прострочені. Успішні функціональні тести не закривають цих питань.

## Межі та метод

- Переглянуто архітектуру, чергу, арбітр, збереження результатів, моделі,
  завантаження, аудіо, ключові frontend controllers, конфігурацію та CI.
- Виконано повний backend STUB suite із branch coverage, frontend unit suite
  із coverage, наявні Playwright E2E, lint, typecheck, build, перевірки
  OpenAPI, dead code, dependency consistency, tracked secrets і Python/npm audits.
- Для помилок конкурентності виконано окремі ізольовані відтворення.
  Тимчасовий frontend-файл із трьома сценаріями прибрано після перевірки.
  Вони перевіряли наявність описаної помилкової поведінки, а не її виправлення.
- Функціональний код, `.env`, користувацькі моделі та робочу БД не змінено.
- Реальні GPU/аудіопристрої, довготривале навантаження, чиста інсталяція,
  ROCm і MPS у цьому аудиті не перевірялися. Наслідки для VRAM, позначені
  нижче як ризики, не є результатами апаратного вимірювання.

Позначення: **P1** — виправити на першому етапі стабілізації; **P2** — наступний
етап; **P3** — невеликий борг. «Відтворено» означає виконаний ізольований
сценарій; «підтверджено кодом» означає перевірений шлях без повного апаратного
відтворення. Оцінка P1 тут не означає доведену критичну security exploitability.

## Знахідки стабільності

### F1. Нотатки можуть втрачати введений текст — P1, відтворено

Джерело: [NotesPanel.tsx](../frontend/src/components/NotesPanel.tsx#L55),
особливо рядки 55–82.

Автозбереження запускається через 650 мс. Cleanup лише скасовує таймер.
При переході в інший workspace до спрацювання таймера запиту збереження немає,
а локальний draft зникає разом із компонентом.

Другий сценарій: запит зі значенням `first draft` уже пішов, користувач вводить
`newer draft`, потім повертається стара відповідь. `setNotes` змінює об'єкт
`active`, ефект `[active]` повертає редактор до `first draft` і скидає `dirty`.
Новий текст зникає, другий save не виконується. Фоновий refresh також може
змінити `active` під час редагування.

**Спрощення:** draft за `noteId` із revision; один послідовний save на нотатку;
відповідь збереження підтверджує тільки відповідну revision. Завантаження списку
не повинно перевстановлювати dirty draft. При переході draft потрібно зберігати
поза компонентом і завершувати save. Критерій: обидва сценарії вище зберігають
останній введений текст.

### F2. Одна помилка БД може назавжди зупинити чергу — P1, відтворено

Джерела: [scheduler.py:137](../backend/app/core/scheduler.py#L137),
[main.py:459](../backend/app/main.py#L459).

`_loop()` не має межі відновлення навколо `_requeue_orphans()`, `_pick_next()`
та помилок, що виходять із `_run()`. Помилка читання/commit БД завершує task.
Те саме можливе, якщо після помилки generation не вдається записати `fail()`.
`notify()` встановлює Event для вже завершеного task; автоматичного restart немає.
Health продовжує повертати `status: ok` без перевірки task worker.

Ізольоване відтворення помилки `_pick_next()` дало:
`task_done=true`, `_running=true`, після `notify()` кількість спроб залишилася 1.

**Спрощення:** явний стан worker `starting/running/degraded/stopped`, обмежений
retry/backoff для transient DB errors і контроль завершення task. Рішення щодо
вже захопленого job має зберігати його стан і не повторювати generation без
перевірки результату. Додати worker readiness у diagnostics/health. Критерій:
одноразова lock-помилка не потребує перезапуску всього продукту.

### F3. Політика GPU-володіння не охоплює всі шляхи — P1, підтверджено кодом і STUB probe

Джерела: [voice_engine.py:420](../backend/app/api/voice_engine.py#L420),
[engine.py:410](../backend/app/services/voice_engine/engine.py#L410),
[arbiter.py:351](../backend/app/core/arbiter.py#L351),
[tts.py:143](../backend/app/api/tts.py#L143),
[transcription.py:193](../backend/app/api/transcription.py#L193),
[embedding_service.py:94](../backend/app/services/embedding_service.py#L94).

- Offline Voice `/convert` завантажує та використовує модель через engine
  без reservation арбітра і без заборони одночасного live-сеансу.
- TTS та transcription при ввімкненому GPU використовують `gpu_lane()`, але
  він викликає `activate_lane()` з `exclusive=False`. Такий lane дає статус,
  проте не блокує завантаження основної моделі й не резервує бюджет пам'яті.
- Embedding server із `embed_gpu_layers > 0` запускається окремо без lease.
- Після зупинки live Voice `shutdown_voice_session()` не викликає
  `engine.unload()`. Engine зберігає посилання на модель після звільнення lane.

STUB probe підтвердив: усередині активного TTS lane арбітр успішно завантажив
image backend; статус одночасно містив resident і lane, `exclusive=false`.
TTS/transcription/embeddings за замовчуванням CPU; ризик їх конкуренції за VRAM
виникає після ввімкнення GPU. Voice за замовчуванням CUDA. Розмір залишкової
Voice VRAM та фактичний OOM тут не вимірювалися.

**Спрощення:** один явний контракт reservation для будь-якого GPU consumer:
власник, режим сумісності, бюджет, release після завершення роботи. Першим
етапом можна серіалізувати GPU audio через наявний механізм; CPU лишається
незалежним. Тестувати одночасні image + offline Voice, live + offline Voice,
image + GPU TTS/transcription та GPU embeddings.

### F4. Скасування/timeout може звільнити ресурс до завершення роботи — P1, частково відтворено

Джерела: [realtime.py:480](../backend/app/services/voice_engine/realtime.py#L480),
[realtime.py:900](../backend/app/services/voice_engine/realtime.py#L900),
[voice_engine.py:68](../backend/app/api/voice_engine.py#L68),
[transcription.py:201](../backend/app/api/transcription.py#L201),
[tts.py:150](../backend/app/api/tts.py#L150).

`RealtimeSession.stop()` чекає thread максимум 5 с, потім без перевірки
`is_alive()` прибирає посилання на worker і processor. `stop_session()` очищає
singleton у `finally`; API також у `finally` звільняє lane та будить чергу.
Якщо inference завис/триває довше, нова задача може початися до його завершення.
Probe з worker, який лишається alive після join, підтвердив очищення обох посилань.

Для transcription timeout скасовує await `to_thread`, але не сам thread;
контекст lane уже завершується. TTS обробляє timeout, однак окремої гарантованої
зупинки subprocess при `CancelledError` немає. Аналогічні межі між coroutine
і реальною ML-роботою слід перевірити у shutdown основних backends.

**Спрощення:** відокремити `stop requested` від `execution finished`. GPU
reservation має жити до реального завершення. Якщо потрібен жорсткий timeout
для невідповідного ML runtime, процес дає контрольоване примусове завершення.
Критерій: завислий thread/process не залишає систему у стані «GPU вільний».

### F5. Два одночасні запити запускають два download workers — P1, відтворено

Джерела: [model_download_service.py:203](../backend/app/services/model_download_service.py#L203),
[model_download_service.py:316](../backend/app/services/model_download_service.py#L316),
[downloads.py:94](../backend/app/api/downloads.py#L94).

Перевірка `_status.state` і перехід у `running` відбуваються в різних critical
sections, між ними є preflight. У router після `start()` ще раз перевіряється
глобальний `is_downloading()`, що не показує, який запит захопив запуск.
Навіть `start()`, який повернув статус уже наявного запуску, може спричинити
новий `create_task()` у router.

Відтворення з двома паралельними API-викликами та barrier у preflight
запустило `run_blocking()` **2 рази замість 1**. Можливі одночасний запис тих
самих файлів і взаємне перетирання progress/error state.

**Спрощення:** admission і створення task належать одному manager; `start()`
повертає конкретний `download_id` або conflict. Manager зберігає task та його
помилку. Критерій: одночасні curated/custom start дають одного власника запуску.

### F6. Chat має гонки вибору розмови та неповне відновлення stream — P1

Джерела: [useChatPanelController.ts:210](../frontend/src/components/useChatPanelController.ts#L210),
[ChatPanelHooks.ts:46](../frontend/src/components/ChatPanelHooks.ts#L46),
[ChatPanelHooks.ts:109](../frontend/src/components/ChatPanelHooks.ts#L109),
[useAppController.ts:373](../frontend/src/useAppController.ts#L373).

**Відтворено:** розпочати повільне завантаження A, потім вибрати B, отримати
B, а потім A. `activeId` лишається B, але `messages` уже від A. Немає request
revision/AbortController або перевірки id перед застосуванням відповіді.

**Підтверджено кодом:** `useChatStream` має окремий WebSocket через
`useEvents(onChatEvent)` без `onConnect/onReconnect`. Якщо terminal event
пропущено, `busy/activeJob` не звіряються з БД. Кореневий reconnect оновлює jobs,
GPU, images, videos, downloads, але не повідомлення активної розмови. Також
stream змінює «останнього assistant», а не повідомлення за стабільним id;
перехід між розмовами не від'єднує його від старого job.

**Спрощення:** один спільний event transport; стан чату за
`conversationId/messageId/jobId`; revision для асинхронного вибору;
reconciliation активної розмови на connect/reconnect. Критерії: повільний A
не змінює B; після розриву під час generation видно фінальну відповідь і
коректний busy state; токени A не потрапляють до B.

### F7. Поточні Python locks не проходять dependency release gates — P1

Джерела: [audit-allowlist.json](../backend/audit-allowlist.json),
[ci.yml](../.github/workflows/ci.yml), [dependency-profiles.json](../backend/dependency-profiles.json).

Foundation/dev/GPU scanners повідомили findings, наведені в таблиці перевірок.
Винятки `transformers` діяли до **2026-10-31**, `setuptools` до **2026-09-15**.
Перевірка allowlist на дату аудиту завершується
`expired audit exception PYSEC-2025-217 for transformers (2026-10-31)`.
Release workflow залежить від CI, отже ці gates блокують реліз для такого стану locks.

**Дія:** окремо оновити foundation/dev graph, перекомпілювати hashes через
manifest workflow, повторити audits і функціональні перевірки. GPU graph
оновлювати сумісним набором із реальною smoke-матрицею. Findings scanner
потребують triage за досяжними шляхами; просте перенесення expiry не усуває ризик.

### F8. Rescan оновлює descriptor, але залишає старий backend — P2, відтворено

Джерела: [registry.py:135](../backend/app/backends/registry.py#L135),
[registry.py:346](../backend/app/backends/registry.py#L346).

`scan_async()` замінює descriptors/loras; `_backends` зберігається. `get_backend()`
повертає кеш до перевірки поточного descriptor. Після зміни моделі/projector
зі збереженим id runtime може мати старі path, quant або mmproj.

Probe після заміни inventory: `get_descriptor().path = new.gguf`,
`get_backend().descriptor.path = old.gguf`. Шляхи settings позначені як
restart-required, але rescan також потрібен для змін файлів у поточних каталогах.

**Спрощення:** snapshot/version descriptor і звірка backend cache з ним;
незайняті старі backends прибирати, зайняті замінювати після release через
арбітр. Критерій: metadata API та фактично використаний backend узгоджені.

### F9. Video artifacts мають слабший lifecycle, ніж images — P2, підтверджено кодом

Джерела: [scheduler.py:337](../backend/app/core/scheduler.py#L337),
[video_diffusers.py:479](../backend/app/backends/video_diffusers.py#L479),
[job_results.py:155](../backend/app/core/job_results.py#L155),
[gallery_service.py:158](../backend/app/services/gallery_service.py#L158).

При cancel після `backend.generate()` image/upscale видаляють незареєстровані
файли через `discard_images()`. Video лише позначає job canceled; MP4, poster,
thumbnail і JSON уже можуть лишитися на диску без історії. `_persist()` пише
відразу у фінальні файли без загального rollback для часткового результату.
Автоматичне recovery історії працює для PNG, не відновлює Video rows із MP4.

**Спрощення:** спільний невеликий контракт artifacts: paths + metadata,
тимчасовий output, finalize після успіху, idempotent cleanup/recovery. Критерії:
cancel під час encode і failure poster/DB commit не залишають невраховані
великі файли; успішний результат відновлюється після рестарту.

### F10. GPU audit неправильно перевіряє пропущені пакети — P2, відтворено

Джерело: [audit_gpu_lock.py:48](../scripts/audit_gpu_lock.py#L48).

Код шукає `skip_reason` у `report["fixes"]`; фактичний pip-audit JSON
містить його в `report["dependencies"]`. При порожньому allowlist probe з
довільним unaudited dependency повернув `[]` errors. Поточний звіт scanner
має пропущений `torchaudio`, якого також немає у `EXPECTED_UNAUDITABLE`.

Прострочена allowlist наразі зупиняє перевірку раніше, але після її виправлення
ця прогалина залишиться.

**Дія:** читати реальний формат dependency entries, перевіряти exit status
scanner та покрити fixture із його актуальним JSON. Skip потребує явної
окремої політики та не повинен автоматично вважатися перевіреним пакетом.

### F11. Cancel endpoint публікує неправдивий terminal event — P2, підтверджено кодом

Джерела: [jobs.py:445](../backend/app/api/jobs.py#L445),
[queue_service.py:53](../backend/app/services/queue_service.py#L53).

Для job, який уже `done/error/cancelled`, `queue_service.cancel_job()` не змінює
статус, однак router безумовно публікує `JOB_CANCELLED`. Для `running` результат
`worker.cancel_running()` ігнорується. Це залишає REST і events з різним
описом переходу та ускладнює повторні запити/cancel на межі завершення.

**Спрощення:** одна функція переходу стану з результатом `changed/current`;
event тільки після реального durable transition. Перевірити повторний cancel,
cancel після done і cancel між вибором job та початком виконання.

## Де код перевантажений і як його зменшувати

Фізичні рядки включають порожні рядки/коментарі. Backend: **28 642 рядки,
123 Python-файли**, включно з vendored RVC. Frontend: **20 210 рядків,
84 файли**, без tests і generated types, включно з CSS. У backend 25 файлів
мають понад 400 рядків, у frontend — 19. Розмір допомагає вибрати місце
перегляду; сам по собі не доводить поганий дизайн.

### React controllers: забагато станів і відповідальностей

| Модуль | Рядки | Виклики useState / useEffect | Полів у головному return |
|---|---:|---:|---:|
| `useChatPanelController.ts` | 678 | 36 / 8 | 100 |
| `useVoiceSessionController.ts` | 782 | 35 / 7 | 8 груп із багатьма props |
| `useAppController.ts` | 634 | 32 / 9 | 62 |
| `useImageComposerController.ts` | 480 | 19 / 8 | 60 |

**Chat:** контролер одночасно веде розмови, sampling, personas, attachments,
import/export, llama runtime і UI. Виділити стани conversation/stream,
sampling draft та runtime settings за їхніми життєвими циклами. Для пов'язаних
полів використати reducer з діями `conversationLoaded`, `draftChanged`,
`generationStarted/Finished`. Це прибирає часткові оновлення наборів setter-ів.
Зберігати state і events за id, що також вирішує F6.

**Voice:** об'єднати `routingDraft`, `tuningDraft`, `sessionState`. Polling і
apply мають спільні revision, щоб повільний status response не повертав старі
налаштування. Прибрати з активного frontend draft legacy `formantShift` і
`inputGateDb`: helper все одно надсилає константи 0/-90, а backend нейтралізує
ці поля. Legacy wire compatibility можна лишити на межі API.

**App:** відокремити app preferences/navigation від server snapshots і event
dispatch. Зараз auth, cache, notifications, GPU telemetry, history, routing
між workspaces і drafts зібрані в один return. Залишити один зрозумілий шлях
отримання/оновлення snapshot із контролем застарілих відповідей.

**Image composer:** параметри, touched flags і preset selection є одним draft.
Reducer може атомарно виконувати `applyPreset`, `changeFamily`, `editField`,
`reproduce`. Зберегти поточні правила touched/defaults та їхні поведінкові
перевірки. Винесення setter-ів у новий файл саме по собі не зменшує складність.

Наявних React primitives достатньо для першого етапу; новий state framework
не є передумовою цих змін.

### Image backend: 9 mixins зі спільним неявним станом

Джерела: [image_diffusers.py:41](../backend/app/backends/image_diffusers.py#L41),
[generation.py](../backend/app/backends/image_diffusers_parts/generation.py).

Image backend разом із parts package має **3 101 рядок**. Клас успадковує
9 mixins та `ImageBackend`. Mixins змінюють спільні `_pipe`, caches, accelerator,
LoRA і lifecycle flags. Generation helper приймає `backend: Any` і викликає
багато приватних методів; контракт між файлами лишився неявним.

Перший крок — типізований Protocol для generation залежностей і явний runtime
context. Далі відокремити family loader/adapter від ownership, cleanup і
persistence. Починати з однієї сім'ї та зберігати поведінку. Центральні
memory/lease правила мають лишитися єдиними, із реальною GPU smoke-перевіркою
після зміни lifecycle.

### Дублювання контрактів та джерел істини

- `JobCreate.params` лишається довільним dict, image має додаткову Pydantic
  перевірку, а video значною мірою нормалізується у router. Згенеровані TS-типи
  не дають повного контракту для такого payload. Ввести typed params для
  video/LLM/upscale і єдину межу валідації, зберігши сумісність API.
- Family defaults/capabilities повторюються у backend loaders, API validation,
  settings та frontend helpers/presets. Backend має повертати effective
  defaults, dimension grid і supported modes для моделі. Frontend presets
  можуть лишитися творчими наборами, що користуються цим контрактом.
- `runtime_settings()` вручну перелічує близько сотні рядків налаштувань,
  паралельно існує metadata `SPECS`. Для Settings view використати один
  опис; окремий diagnostics payload залишити для фактичного runtime state.
- `model_download_service` використовує installer catalog через scripts.
  При наступній зміні каталогу спільну декларативну частину варто винести
  у звичайний importable module; HTTP service не має залежати від CLI side effects.
- Bootstrap/install/update уже мають shared profile resolver. Наступне
  спрощення — спільний план дій і тонкі platform wrappers; зберегти
  безпечні перевірки ports/PID та наявні launcher tests.

### Прогалини перевірок, які мають практичну ціну

- `useAppController`, `useVoiceSessionController`, `useImageComposerController`
  мають **0% unit coverage**; `NotesPanel` також 0%. E2E є окремим шаром і
  не входить до цього coverage, але наявні 10 сценаріїв не перевіряють
  races автозбереження чи перемикання чатів.
- Браузерні E2E використовують API stubs. Їхній успіх не перевіряє повного
  зв'язку browser → FastAPI → SQLite; backend ASGI integration tests
  виконуються окремо.
- Backend combined coverage: `api/chat.py` **39.8%**, `api/jobs.py` **47.3%**,
  `api/downloads.py` **31.0%**, `core/job_results.py` **65.1%**,
  image LoRA runtime **7.3%**. Це напрями для поведінкових перевірок, а не
  вимога підняти кожен файл до однакового відсотка.
- `realtime.py` цілком виключений із coverage разом з апаратними adapters.
  Thread/session lifecycle можна тестувати fake workers/devices без GPU;
  його варто винести з апаратної частини та включити у вимірювання.
- Високе coverage scheduler (**98.7% combined**) не виявило F2: проходження
  рядків не замінює перевірку того, що worker переживає помилку persistence.
- Для frontend повного test typecheck немає: основний tsconfig виключає
  `src/**/*.test.*`. Додати окремий test tsconfig після стабілізації fixtures.

## Додатковий борг

- **P2:** edit/regenerate чату виконує `truncateFrom()` перед окремим `submit()`
  (`ChatPanelHooks.ts`). Якщо другий запит не дійде, попередня гілка історії
  вже видалена. Доцільний атомарний backend use case або збереження попередньої
  версії до успішного enqueue. Сценарій збою в цьому аудиті окремо не запускався.
- **P2, масштабування:** startup очікує повного сканування output tree й ремонту
  thumbnail до readiness (`main.py`, `gallery_service`). I/O винесено у threads,
  але велика історія може подовжувати запуск. Спершу виміряти 1k/10k outputs,
  потім запровадити incremental/background reconciliation із прогресом.
- **P3:** прибрати непотрібний export `OutpaintMargins`, щоб повернути Knip gate.
- **P3:** `VoicePanelSections.tsx` зараз лише перевидає exports із шести файлів.
  Такий barrel можна прибрати, якщо він не задає потрібної публічної межі.
- Backup копіює БД і manifest outputs; settings/voice JSON та самі media bytes
  ним не захищені. Це задокументована межа поточного інструмента. Для
  продуктового restore сценарію потрібна явна інвентаризація всіх user assets.

## Послідовність робіт

### Пакет 1 — дані, відновлення та поточні червоні gates

1. F1: note draft/revision/save lifecycle; перевірки переходу і старої відповіді.
2. F2: worker recovery та readiness; fault injection для select/commit/fail.
3. F5: один власник download task; parallel curated/custom API tests.
4. F6: request revision для вибору чату, binding stream до ids,
   reconnect reconciliation.
5. F7/F10: dependency triage, виправлення parser skips, актуальні locks;
   GPU upgrade окремо з hardware validation. Прибрати Knip blocker.

### Пакет 2 — одна модель життєвого циклу ресурсів

1. F3/F4: спільний reservation contract для GPU audio/embeddings і основної
   черги; release після фактичного завершення thread/process.
2. F8/F11: cache invalidation за descriptor і явні idempotent job transitions.
3. F9: єдиний finalize/cleanup/recovery для generated artifacts.
4. Перевірити Voice → Image → LLM → Video, cancel/load/encode timeout,
   повторні swap cycles, залишкові RAM/VRAM і subprocesses на реальному GPU.

### Пакет 3 — спрощення станів та внутрішніх контрактів

1. Chat/Voice draft reducers і межі відповідальностей controllers.
2. Image composer draft reducer зі збереженням touched/default semantics.
3. Типізований image runtime context/Protocol, поступове зменшення mixin coupling.
4. Typed job params та централізовані effective model capabilities/defaults.
5. Вимірювання startup на великій історії та спрощення runtime/bootstrap policy.

Зміни варто робити окремими невеликими commits: поведінкова перевірка збою,
виправлення або спрощення відповідного шляху, релевантні checks. Критерій
завершення стабілізації: збереження переживає навігацію/повільну мережу,
черга переживає transient faults, reconnect відновлює стан, GPU reservations
відповідають фактично живій роботі, release gates проходять на актуальну дату.

## Що зберегти

- Центральний арбітр і серіалізацію основної GPU-черги.
- Спільну scheduler policy для виконання та plan preview.
- Ізольовані STUB tests і справжні апаратні smoke gates як окремі перевірки.
- Alembic, SQLite WAL/busy timeout та явні транзакції.

чіткі правила збереження, переходів стану та володіння ресурсами на їхніх межах.

## Реалізація першого пакета після аудиту

Пакет охоплює F1, F2, F5, F6, F10 і Knip blocker. Решта знахідок лишається
відкритою; апаратні та dependency gates не позначаються пройденими.

| Пункт | Реалізована поведінка |
|---|---|
| F1 | `NoteDrafts` зберігає draft поза компонентом і в browser storage, серіалізує saves за noteId, відрізняє підтверджену revision від новішого вводу. Навігація flush-ить чернетку, помилка має Retry save. |
| F2 | Worker контролює bootstrap/selection/persistence faults із backoff, повторює тільки terminal persistence після помилки виконання, зберігає вже committed terminal results. Startup очікує готовності обмежений час; health відображає worker state. |
| F5 | Один admission lock охоплює curated/custom preflight і перехід у running. Router запускає worker лише для запиту, який отримав admission; помилки фонового runner відображаються у status. |
| F6 | Один app WebSocket з workspace subscribers; stream має message/job binding і revision. Старі selection/send responses і токени іншої розмови ігноруються. Reconnect звіряє job chain і durable messages. Assistant зберігає child job id у БД. |
| F10 | Skip detection читає dependencies scanner JSON; неочікуваний exit code та прострочена/некоректна policy дають явну помилку. Винятки не продовжувалися. |
| Knip | `OutpaintMargins` лишився внутрішнім типом editor helpers. |

Додані перевірки відтворюють старі помилки та вимагають нової поведінки:
навігація до autosave, новий ввід під час save, failed draft recovery,
transient DB fault, збій terminal persistence без повторної generation,
concurrent curated/custom API requests, stale conversation/send responses,
повторне надсилання під час creation, reconnect і tool-child recovery.
Окремі браузерні сценарії перевіряють note navigation та chat reconnect із
єдиним активним WebSocket.

Перевірка реалізованого пакета:

- Backend: **677 passed, 1 skipped**, shuffled seed `20261115`; JUnit —
  0 failures / 0 errors. Coverage: **83.54% statements**, **66.92% branches**,
  **80.12% combined**, поріг 75% пройдено.
- Frontend: **148 unit tests**, включно з відновленням лише editable draft
